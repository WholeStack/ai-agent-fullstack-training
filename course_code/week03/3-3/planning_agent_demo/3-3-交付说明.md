因此"调用 pi 的续跑能力"落点为：**低层 journal 判定操作边界 + `runAgentLoopContinue` 从存档 messages 续跑**。

### 1. 已经具备的能力

模型接入（`model.ts`）、Loop 装配与 Hook 接缝（`agent-runner.ts`）、工具执行（`runtime.ts`，含 `apply_patch`/`run_test` 真实退出码）、消息回写与事件流（`observeEvent`）、中断信号（`AbortController`）、计划层（`plan-store.ts`）、计划工具（`plan-tools.ts`）、完成契约（`completion-contract.ts`）、计划门禁与重复保护（`loop-guard.ts`）、目标仓库与待修复缺陷（`fixtures/demo-app/`）、18 个既有测试。

### 2. 还缺的业务逻辑

- R1：无可持久化的任务/步骤运行记录（`TraceEvent` 无输入输出、失败原因、重试、决策、证据）。
- R2：完全没有存档（格式、校验、原子写、失败保留旧档）。
- R3：完全没有恢复（三态判定、结果不明写操作禁止重放、保留计数）。
- R4：完全没有审批（`apply_patch` 通过门禁后立即落盘）。
- R5：无独立工作区重跑。

### 3. 当前不支持，需要说明的限制

无进程内存/调用栈快照；无法恢复原测试子进程；无法做到任意时刻崩溃无损恢复；**不保证副作用恰好一次**；不扩展上下文自动压缩与 Sandbox；不引入事务/调度框架；`AgentHarness.resume()` 上游未实现；模型路径与原错误均不保证复现。

## 二、最小规格（实现的行为）

- **R1**：`TaskRecorder` 按 `AgentEvent`/Hook 实时更新 `TaskRecord`。每步记工具调用 ID、输入、输出、失败原因、`attempts`、`nextDecision`、`evidenceIds`。运行状态是一台显式状态机（`running` / `waiting_tool` / `waiting_approval` / `suspended` / `completed` / `failed` / `cancelled`），**每次迁移都写进 `transitions`**（含自环），因此"为什么停在这里、恢复后接着谁"可以逐条核对。状态含 `suspended`、`waiting_approval`，**均不计失败**；人工暂停（`--pause-after`）不改变状态，任务仍是 `running`。完成只由证据 + 测试退出码裁决；`completed/failed/cancelled` 为终态，不再续跑。
- **R2**：存档 `<projectRoot>/.agent-runs/<runId>.json`，信封 `schemaVersion`（v2）`+ runId + createdAt + seq + payload + checksum`。`payload` 含 task（含 transitions 与 `counters.checkpoints`）/plan/evidence/session(messages+sessionId)/workspace(id/codeRevision/repoDigest)/pendingApproval/decisions/counters。写盘 `tmp + rename` 原子替换；校验失败即拒绝。保存失败抛 `CHECKPOINT_WRITE_FAILED`、保留旧档、不推进。同一工作区里同 `runId` 的**未终结**存档不会被新运行静默覆盖：新运行直接拒绝（exit 3）并提示改用 `--resume`，终态存档覆盖前会打印提示。
- **R3**：`prepareResume()` 顺序固定：校验存档 → 校验工作区 → 校验任务非终态 → 还原计划/证据/记录 → `runAgentLoopContinue` 续跑（**回灌存档里的会话历史**，不再重发任务输入；若存档停在"助手刚说完话"的轮次，续跑前补一条推进提示）。三态：`completed`/`not_started`/`unknown`；`unknown` 写操作禁止重放并停自动推进；无完整测试结果不得记 completed；保留轮数/重试/预算。**有待审批动作时，检查结果会带出 `pendingApproval`**：没有决定就不启动模型。
- **R4**：`apply_patch` 先 `planPatch()`（只读 + 算 `patchHash`）并 `stage()`，进入 `waiting_approval`，不落盘。批准入口有两个，且**都不在模型可见的工具里**：人工 `--resume <id> --approve/--reject`（`by:"manual"`）与显式 `--auto-approve`（`by:"auto"`），两者共用 `approval-flow` 的同一段执行逻辑。批准只对对应 `actionId`；执行前重算 `patchHash`，变化即 `APPROVAL_STALE`；`reject` 后不可执行。等待期间其它受控写被拦。待审批动作随存档跨进程传递，但重启后 `approved` 强制为 false。
- **R5**：`createFreshRunPlan()` 用原任务输入 + 初始代码复制到新工作区（`--replay`），新 `runId`，`dangerousPermissions:false`，原存档只读；报告里并排打印原运行与本运行的测试范围/退出码，供对照。

**明确不实现**：内存/栈快照、测试子进程恢复、任意时刻无损恢复、exactly-once、上下文压缩、Sandbox、事务/调度框架。

### 本次实现顺带修掉的既有缺陷

做 `--pause-after` / `--auto-approve` 实验时暴露了这些既有问题，都不是新参数引入的：

| 缺陷 | 表现 | 原因 | 修法 |
|---|---|---|---|
| 恢复后证据重号 | 续跑第一次 `addEvidence` 抛 `duplicate evidence: ev-1`，证据总数停在 3 | `PlanningSession.restore` 还原证据时 `EvidenceStore.sequence` 仍为 0 | 还原带 ID 的证据时把计数推到已用序号之后（`plan-store.ts`） |
| 恢复后代码版本对不齐 | 完成步骤时 `PLAN_EVIDENCE_STALE` | 存档 `codeRevision` 比证据里的最高版本旧一版 | 以存档证据的最高 `artifactVersion` 为准还原 runtime 版本（`agent-runner.ts`） |
| `run_test` 静默失败 | 所有测试 `exit=1` 且输出为空，只用 2ms | `child-run.ts` 用 `new URL(...).pathname` 拼 `runtimeRoot`，路径里的空格没解码成 `%20`，`execFile` 直接 ENOENT | 改用 `fileURLToPath`（`scripts/child-run.ts`） |
| 步骤卡在等待审批 | 批准后步骤仍是等待审批态，下游 verify 无法开始 | 审批把**步骤**状态也改掉了，批准后要再还原一次 | 等待审批只改**任务**状态：步骤保持 `in_progress`，`clearApproval` 不再需要还原步骤（`task-record.ts`） |
| 一次补丁两条 diff 证据 | auto 批准后 `ev-N` 整体错位，下游 `update_plan_step` 对不上证据 | 审批执行段登记了一次证据，`observeToolResult` 又照着同一份工具结果登记一次 | auto 路径返回时摘掉 `evidence`，证据只登记一次（`pi-tools.ts`） |
| 对照表读不到退出码 | 重跑对照里所有测试都是 `exit=unknown 未通过` | `summarizeTests` 读工具结果的浅层字段，而退出码记在证据 payload 里 | 从 `evidence.payload` 读 `scope`/`exitCode`（`fresh-run.ts`） |
| 结果不明被噪声淹没 | 早先回合已成功的 `run_test` 也被报成"结果不明" | journal 只记「工具启动」，同属一个未闭合操作的历史调用全都算上了 | 用存档里的工具调用记录判完成（有 `endedAt` 即为已完成）再决定是否报 unknown（`resume.ts`） |
| 恢复后从头重做一遍 | 同一任务恢复后模型把仓库整个重读一遍（迁移从 `list_files` 重新开始），一直跑到第 29 轮才做完；`runAgentLoopContinue` 实际上是死路径 | `persist` 写的是 `context.messages`，而 pi 的 `runAgentLoop` 内部用 `{...context, messages: [...]}` 的副本，**从不回写调用方的那个数组**——存档里的 `session.messages` 恒为 `[]`，恢复时 `restored?.messages?.length` 为 0，于是走 `runAgentLoop([prompt])`：任务输入重发一遍、上下文清零 | 按事件累积会话历史：`message_end`（role: user，覆盖任务输入与 `FINAL_REJECTED` 追加提示）+ `turn_end`（助手消息 + 本轮工具结果），存档与续跑共用这一份（`agent-runner.ts`） |
| 续跑入口直接抛错 | 存档恰好停在"助手刚说完话"的轮次时，续跑入口抛 `Cannot continue from message role: assistant` | pi 的续跑入口要求历史非空、且最后一条不是 assistant | 这种情况续跑前补一条推进提示 `RESUME_CONTINUE_HINT`，再走续跑入口（`agent-runner.ts`） |
| 暂停中的存档被静默顶掉 | 同一工作区用同一个 `--run-id` 再开一次新运行，上一次的轮数/证据/迁移整体消失，"暂停 → 继续"没法反复做 | `checkpointPath(projectRoot, runId)` 是同一个路径，`tmp + rename` 直接替换，没有任何冲突检查 | 新运行遇到同 runId 的**未终结**存档直接拒绝（exit 3）并提示改用 `--resume`；终态存档覆盖前打印提示（`cli.ts`） |

幂等重放也补了：恢复时重复提交同一补丁，锚点已消失且替换结果已就位，
按 `PATCH_ALREADY_APPLIED` 放行且不推进代码版本，不再误报 `PATCH_ANCHOR_NOT_FOUND`。

## 四、明确"未覆盖"

| 项 | 原因 |
|---|---|
| 进程内存/调用栈快照恢复 | pi 0.84.4 无该接口；本任务明确不实现 |
| 原测试子进程恢复 | `execFile` 句柄未持久化；只判定"结果不明"后隔离重跑 |
| 任意时刻崩溃无损恢复 | 仅保证"完整轮次结束"与"审批前"两个存档点 |
| 副作用恰好一次 | 无事务；以"写前记录 + 恢复时校验差异"逼近 |
| pi `AgentHarness.resume()` | 上游 0.84.4 未实现，抛 `HarnessNotImplemented` |
| 上下文自动压缩 / Sandbox | 明确不实现 |
| 真实 Gateway 端到端验收 | 逐条断言的验收用 faux 模型（可重复）；真实 Gateway 只跑了"中断 → 恢复"闭环（`npm run lab:cycle`，见下方证据），未对每个验收点都跑一遍真实模型 |
| 审批状态持久化 | `approved` 只存在于做出决定的那次进程；重启后必须由人工重新批准，或再次显式 `--auto-approve` |

## 五、已知取舍

| 歧义 | 取舍 | 理由 |
|---|---|---|
| "完整轮次结束"边界 | `turn_end` 后、下一轮前，在 `observeEvent` 中 `await persist` | 与 pi Hook 时机一致，且避免 fire-and-forget 竞态 |
| `unknown` 是否允许重跑读 | 允许 | 读无副作用，journal 标 `replay:"safe"` |
| `repoDigest` 范围 | 仅目标源码 + 相关测试文件 | 全仓会被 node_modules/临时文件干扰 |
| 审批粒度 | 单个 `apply_patch` action | 对应"批准只适用于对应动作" |
| 存档位置 | 工作区内 `.agent-runs/` | 异常退出实验只在临时工作区 |
| `MODEL_ERROR` 归类 | `suspended`，非 `failed` | 模型/网关错误是可重试暂停，不是任务失败 |
| 测试失败 vs 结果不明 | exit=1 属"结果明确未通过"；只有拿不到退出码才是 unknown | 避免把失败误判为不明 |
| `messages` 全量存档 | 全量，不压缩 | 明确不引入上下文压缩 |
| 人工暂停后的状态 | 仍是 `running`，不置 `suspended` | 暂停只是"停在这个存档点"，任务没有失败、也不在等任何东西；恢复时据此直接续跑 |
| 批准入口放在哪 | 命令行（`--approve/--reject/--auto-approve`），模型侧不暴露 | 模型能批准自己提交的补丁时，"审批"就只剩提示词约束，控制不了执行 |
| 审批策略是否跨进程继承 | 不继承，必须每次显式声明 | `--auto-approve` 是操作者对**这次**进程的授权；静默继承会让"重启后危险操作被自动放行"变得不可见 |
| 拒绝之后 | 运行停在 `suspended`，计划步骤记 `failed`，不再启动模型 | 拒绝是人工决定，不是任务失败；但被拒绝的修复尝试也不算数，要换方案就得走修订或重新发起 |
| 待审批动作是否入档 | 入档（含完整 args 与 patchHash），但 `approved` 不入档 | 换进程后必须看到同一份补丁、同一个哈希，才能判断"批的是不是这一份" |
